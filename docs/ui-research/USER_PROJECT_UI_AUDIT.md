## Part I — Android / mobile repositories

### 1. jarvis-agent — Kotlin AI assistant (Views/XML)

Repo: `Bilal140202/jarvis-agent`. The Android app lives in the nested `jarvis-agent/` subfolder (the root also hosts landing pages, docs, and a worklog).

**Visual design.** Palette defined in `jarvis-agent/app/src/main/res/values/colors.xml`: `primary #6C63FF` (periwinkle purple), `primary_dark #4A42D4`, `accent #FF6B6B` (coral, also reused as `error`); a 3-step dark navy elevation ladder `background #0F0F1A`, `surface #1A1A2E`, `surface_light #2A2A4E`; `text_primary #E0E0E0`, `text_secondary #808080`; `success #4CAF50`; and a one-off `#FFD700` gold for starred tasks (`res/layout/activity_main.xml:446`). Dark-only: `themes.xml` declares a single `Theme.JarvisAgent` on `android:Theme.DeviceDefault.NoActionBar` — no `values-night/`, no light mode. The purple/navy duotone is a coherent identity, but it is undermined by stock `@android:drawable/ic_menu_*` icons (`activity_main.xml:31, 78, 221`) — no custom iconography anywhere.

**Layout.** No Jetpack widgets: a hand-rolled left drawer and right task-history drawer built as `FrameLayout` overlays with `#AA000000` scrims, toggled via `visibility` in `ChatActivity.kt` (lines 224-243). The chat list is a `ListView` with `stackFromBottom` + `transcriptMode="alwaysScroll"` (`activity_main.xml:87-97`) — a one-line stick-to-bottom chat pattern worth remembering for prompt-history surfaces. Onboarding is a 3-step dot indicator (`dot0..dot2` with presence drawables) plus a `contentArea` FrameLayout that steps are inflated into (`activity_onboarding.xml:37-60`, `OnboardingActivity.kt`).

**Interaction.** Plain `kotlinx.coroutines` scopes inside `ChatActivity.kt` (722 lines; imports at 34-36); no ViewModel/LiveData/StateFlow. Zero animation code (no animators or transitions found) — drawers pop, nothing eases. Accessibility is genuinely decent for a solo project: `contentDescription` on every ImageButton ("Menu", "Voice input", "Send", "Task History", "Close"), 44dp icon targets, `minHeight 44dp` input, `clickable`+`focusable` menu rows (`activity_main.xml:33, 80, 114, 138, 456, 212-216`).

**Implementation quality.** The central defect: `colors.xml` exists but layouts ignore it — `activity_main.xml` hardcodes raw hex everywhere (`android:background="#0F0F1A"`, `android:textColor="#E0E0E0"`, lines 6, 24, 52, 126, 160, 448, …). The token file is decorative, not enforced. Typography is ad-hoc sizes 11sp/12sp/13sp/14sp/15sp/16sp/18sp/22sp/48sp inline in layouts (e.g. `activity_main.xml:53`, `activity_onboarding.xml:16`); no defined scale. The wordmark uses 48sp bold + `letterSpacing 0.1` (`activity_onboarding.xml:12-20`). Chat bubbles are the only shape token: 16dp-rounded rectangles — assistant bubble `#1A1A2E` with 1dp `#2A2A4E` stroke, user bubble solid `#6C63FF` (`res/drawable/bg_message_assistant.xml`, `bg_message_user.xml`). Menu strings are hardcoded in layouts; `strings.xml` holds only 6 entries — effectively no i18n.

**Ratings:** visual identity 2.5/5 (nice duotone, stock icons); consistency 2/5 (tokens defined but bypassed); maintainability 2/5 (722-line Activity, hex in layouts).

### 3. Your-Files-Android — file manager (Kotlin, Jetpack Compose)

**Visual design.** Theme-as-data architecture in `app/src/main/java/com/yourfiles/manager/app/uim3/theme/Color.kt`: a `ThemeColors` data class (lines 22-99) carries the full M3 role set for light+dark **plus neutral overrides (nullable, fallback to defaults), a `cornerRadius` seed, card style flags (`cardElevation`, `outlinedCards`, `coloredHeader`), and structural layout parameters** — `itemLayoutStyle` (LIST_ROW/CARD/COMPACT enum), `listItemHeight`, `fileIconSize`, `thumbnailSize`, `showDividers`, `showBreadcrumb`, `gridSpacing`. A theme changes actual UI structure, not just colors. Six named skins in `AppThemeManager.kt:32-358` ("ES Explorer", "Google Files", "MiXplorer", "Material You", "Amaze", "One UI"), each a `ThemeColors` instance with distinct `cornerRadius` (8/16/4/28/12/20), elevation, header treatment and layout style — one composable tree renders six recognizably different looks purely from data. Proper 5-step neutral ramps (`Color.kt:102-139`): `surfaceContainer(Lowest…Highest)` for light (`#FFFFFF`→`#E8E8E8`) and dark (`#0D0D0D`→`#333333`), classic Material dark `#121212` background, `#212121`-based light text; error container roles defined for both modes (141-150). Semantic colors live in one place, `uim3/theme/CategoryColors.kt`: `AppColors` object with Success/Warning/Info/Error plus per-file-category hues (`CategoryImages #E91E63`, `CategoryVideos #9C27B0`, `CategoryAudio #FF9800`, `CategoryDocuments #2196F3`, `CategoryApk #4CAF50`, `CategoryArchives #795548`, `FolderColor #FF9800`) paired with a `CATEGORY_ICONS` map and extension→color resolvers (`categoryColorForExtension`, lines 67-74) — a single source of truth so no screen invents a category color.

**Layout.** Shape derivation formula in `uim3/theme/Theme.kt:12-25`: one `cornerRadius` seed expands to a 5-step M3 shape scale — `xsmall = r*0.3, small = r*0.6, medium = r, large = r*1.4, xlarge = r*2.0` (floors 2/4dp, default seed 12). A cheap, proportionally consistent shape system. Spacing in `uim3/theme/Spacing.kt`: named object `xs 2 / sm 4 / md 8 / lg 12 / xl 16 / xxl 24 / xxxl 32` plus context aliases (`screenHorizontal`, `cardInner`, `listItemVertical`, icon sizes, `thumbnailLarge 120dp`). Compose `NavHost` (7 references), `LocalNavController.kt`, ~20 screens under `presentation/ui/pages/` (FileBrowser, StorageAnalyzer, TrashPage, WhatsAppCleanerPage, …), reusable common components in `presentation/ui/components/common/` — `ScreenScaffold`, `ConfirmDialog`, `LoadingStateCompose`, `PopupCompose`, thumbnail composables per file type.

**Interaction.** Full dual schemes built in `Theme.kt` (`buildLightScheme`/`buildDarkScheme` lines 27-77) from the same `ThemeColors`; `AppTheme(darkTheme, themeColors)` is the single entry point. MVVM: 15 files use ViewModel/StateFlow (`presentation/vm/`). Accessibility: 73 `contentDescription`/`semantics` occurrences across Kotlin sources. i18n: `values-ja`, `values-ko`, `values-zh-rCN` string resources exist.

**Implementation quality.** Typography in `uim3/theme/Type.kt`: downloadable Google Font **Arimo** via `GoogleFont.Provider` with 4 weights (lines 12-25), and a fully populated M3 `Typography` where **every style is annotated with its intended usage** ("displaySmall — '4.7 GB' hero stat", "titleMedium — 'Found So Far', 'Categories'"), 57/45/36/32/28/24/22/18/16/14/12sp scale with per-style letter-spacing. The identity is the theming engine, not one fixed look.

**Visual design.** Modern Flutter M3 pattern in `lib/main.dart:28-53`: `ThemeData(colorScheme: ColorScheme.fromSeed(seedColor: Color(0xFF2196F3)), useMaterial3: true)` with separate light `theme` and `darkTheme` (same Material-blue seed), custom `appBarTheme` (elevation 0, centered title, white icons, w600 20sp title). Splash-gated root: `_showSplash` state swaps `SplashScreen` → `HomeScreen` (`main.dart:18-56`). The look is default Material blue with gradient chrome — generic.

Accessibility is near-absent: 1 occurrence of semantics/tooltip across all of `lib/` (grep). State is `StatefulWidget` + `setState` throughout; no Provider/Riverpod/Bloc.

**Ratings:** visual identity 2.5/5; consistency 2/5 (37 hardcoded hex, empty theme file); maintainability 2.5/5 (triplicate home screens, no a11y, but good folder structure).

### 5. nexpdf — Jetpack Compose PDF app

Repo: `superz1402/nexpdf`. Small but process-exemplary: UI engineering is *documented* before/alongside code.

**Visual design.** Brand palette "Ember" in `app/src/main/java/com/nexpdf/app/ui/theme/Theme.kt:14-51`: warm orange — light primary `#8F4C25` on `#FFF8F6` surface, `primaryContainer #FFDBCB`; dark primary `#FFB68D` on `#201A17` surface, `surfaceContainer #261E1A`. Both schemes hand-tuned across primary/secondary/container/surfaceVariant/container tiers with correct on-colors. Material You integration done right (`Theme.kt:53-71`): `NexPdfTheme(dynamicColor: Boolean = true)` — Android 12+ gets `dynamicLight/DarkColorScheme` (system wallpaper), **falling back to the brand Ember schemes below S or when dynamic is off**. This is the canonical "brand + personalization" pattern.

**Layout.** Written design tokens in `docs/DESIGN_TOKENS.md` (6 principles): content-first; one primary action per screen; motion 200-450ms spring, nothing decorative blocks input, reduced-motion noted as later work; ≥48dp targets, AA contrast via color roles; **shape scale**: cards 16dp / sheets 28dp / buttons stadium / tool chips 24dp; elevation tiers 0/1/3/6dp from tonal roles, "no raw shadows"; screen-enter = fade 220ms + scale 0.96→1, list items 300ms spring, page crossfade 250ms, tool sheet slide-spring; edge-to-edge with innerPadding always respected. Navigation in `ui/AppRoot.kt`: pragmatic string-route switch (`"home"/"viewer:uri"/"annotate:uri"/"tools"/"organizer:uri"`) on `rememberSaveable` state instead of Navigation-Compose — routes carry the document URI as the arg suffix. Deliberately simple for a 5-screen app; fine at this scale, would not scale past it.

**Interaction.** Motion tokens in code (`ui/theme/Motion.kt`): a `NexMotion` object — durations QUICK 120 / STANDARD 220 / EMPHASIZED 320ms; Material easings as `CubicBezierEasing` constants (EmphasizedDecelerate 0.05,0.7,0.1,1.0 etc.); `expressiveSpring()` = `DampingRatioLowBouncy` + `StiffnessMediumLow`. Motion as named constants, not magic numbers. Loading in `ui/common/Skeleton.kt`: a reusable pulse skeleton — `rememberInfiniteTransition` alpha 0.5→1, 700ms `RepeatMode.Reverse` tween, background = `colorScheme.surfaceContainerHighest.copy(alpha = pulse)`, parameterized corner radius; theme-aware, zero hex.

**Implementation quality.** Typography (`ui/theme/Type.kt`): deliberate minimalism — 5 styles only (headlineMedium 28, titleLarge 22, titleMedium 16 @ 0.15sp, bodyMedium 14, labelSmall 11), `FontFamily.Default` to avoid font-license burden in v0.1. The real differentiator is process documentation: `docs/UI_ACCEPTANCE_CHECKLIST.md` is a per-push gate — builds green, insets clean, single primary action, empty/loading/error states all designed, ≥48dp, content descriptions on all icons, scheme-token contrast, motion ≤450ms, "Typography: only MaterialTheme roles" — with honest limitation notes ("no device here… manual on-device testing is on the user"). `docs/SCREEN_INVENTORY.md` tracks per-screen v0.1 status; `docs/UI_RESEARCH.md` and `docs/UI_SPEC.md` also exist. 30 `contentDescription`/`semantics` uses in `ui/`. State is simple; screens take lambdas, no ViewModel yet at this stage (data layer in `data/`).

**Ratings:** visual identity 3.5/5 (warm Ember is distinctive vs. typical blue apps; dynamic color mutes it on A12+ by choice); consistency 5/5 (written spec + tokens enforced); maintainability 5/5 for scale (docs-first, tokens-as-code).

## Part II — Web repositories

### 7. agent-ui-playbook — the owner's UI quality bar (standard, not a product UI)

Repo: `superz1402/agent-ui-playbook` (clone re-verified for this document: `PLAYBOOK.md` 268 lines, `README.md`, `AGENTS.md`, `CHECKLIST.md`, `ATTRIBUTION.md`, `CONTRIBUTING.md`, `CHANGELOG.md`). This is the single most important input for ClipForge: the owner's own written definition of "good UI", written as 13 laws + 4 law candidates, each with Statement / Why / Evidence / Implement / Verify. It was "born from the DmarcDuck build + two Moltbook community critique rounds" (`PLAYBOOK.md` changelog).

**Structure of the standard.** Sections: I. Identity & tokens (Laws 1-2); II. States — the trust triad (Laws 3-5); III. Data & numbers (Laws 6-8); IV. Structure & hierarchy (Laws 9-11); V. Honesty (Laws 12-13); VI. the "AI-generated look" anti-pattern catalog; VII. Agent working rules. Law candidates 14-17 are appended with `Status: candidate` labels. `AGENTS.md` is the paste-ready hard-rules version (12 numbered rules + process rules); `CHECKLIST.md` is the pre-ship checklist where "every item traces to a law"; `ATTRIBUTION.md` is "the scar ledger" with a promotion log; `CONTRIBUTING.md` is the scar protocol ("No receipts → it goes to the idea pile, not the playbook").

**The 13 laws (key phrases, from `PLAYBOOK.md`).** 1. Identity comes from tokens, not components — "Define background / ink / accent / spacing / type-scale as CSS custom properties first (`:root` + `.dark`)"; "One deliberate accent color beats three decorative ones"; Verify: `grep -rE '#[0-9a-fA-F]{3,8}' src/components/` returns nothing outside the token file (PLAYBOOK.md:27). 2. Color never carries meaning alone — "Every status pairs its color with a text label"; grounded in WCAG 2.2 SC 1.4.1 (PLAYBOOK.md:31-39). 3. Loading, empty, and error ship before the happy path counts as done — "Errors always state (a) what happened, (b) why, (c) the next action. Dead-end errors are bugs"; skeletons matching final layout, spinners only for sub-second waits; empty states "teach the next action"; blocking errors get a banner, not a toast (PLAYBOOK.md:47-58). 4. Surfaces must agree, or explain the disagreement — a zero on a filtered view says why it's zero: never stored / outside window / filtered out / failed to load (PLAYBOOK.md:62-70). 5. Presence is not correctness — verification UI distinguishes authorized / missing / wrong-record / lookup-error; otherwise say "unverified — check incomplete", not "verified" (PLAYBOOK.md:74-82). 6. Numbers are a design surface — `font-variant-numeric: tabular-nums` on anything countable; numbers right-aligned; worst-first ordering; monospace for IPs/emails/hashes/IDs; relative dates in dense tables, absolute timestamps in ledgers (PLAYBOOK.md:90-101). 7. A ledger beats a raw table for "what happened to my stuff" (PLAYBOOK.md:105-109). 8. Attribution beats inference — "When the system cannot attribute an outcome to a specific operation, display UNKNOWN. Never render a number inferred from counts" (PLAYBOOK.md:113-119). 9. One loud thing per screen — Verify: "Squint at the screen (or blur it). Does exactly one thing stand out?" (PLAYBOOK.md:127-133). 10. Touch targets and focus are infrastructure — ≥24×24 CSS px (44px mobile web); visible focus rings everywhere; keyboard path through every flow; contrast ≥4.5:1 body / 3:1 large text (PLAYBOOK.md:137-143). 11. No emoji as UI icons — "Iconography comes from a real icon set (lucide-react on web)"; forbid-list: "no gradients, no emoji icons, no cards inside cards, no glassmorphism unless the product is glass"; "forbid-by-name beats adjective guidance because names are checkable" (PLAYBOOK.md:147-153). 12. Honest states over fake polish — real limits in the UI, strikethrough features instead of hiding them, no fake urgency, no confirm-shaming (PLAYBOOK.md:161-165). 13. Positive evidence before mercy — downgrading a scary verdict requires stated evidence; never the verdict (PLAYBOOK.md:169-175). Candidates: 14 "Recognition is not authentication"; 15 "Answer first; length is a loudness problem"; 16 "Motion pays rent (and reduced-motion is honored)" — the repo's own motion budget is "150-200ms ease-out + skeleton pulse only" (`CONTRIBUTING.md`); 17 "The top slot goes to the worst thing you can still do something about".

**Process rules** (`PLAYBOOK.md` §VII / `AGENTS.md`): typecheck + lint + tests + build green before claiming done, then exercise the real flow; fix the test before the product; one screen, one job; screenshot before and after every UI change; single-reporter caution.

**Anti-pattern catalog** (`PLAYBOOK.md` §VI): the purple/indigo-gradient "training-corpus palette", happy-path-only screens, emoji iconography, adjective-driven review, fake completeness, dark-mode bolt-on. Root cause, named in the doc: "an LLM predicts the most likely good design, and the most likely design is the *average* of its corpus. Averaging is exactly what identity is not. The escape … is constraints with reasons and one reference screen to converge on."

## Cautionary anti-pattern list

These are the anti-patterns actually observed across the twelve projects. They are the negative space of ClipForge's UI rules; each entry cites where it was seen.

1. **Token files that code ignores.** jarvis-agent's `colors.xml` vs raw hex in every layout (`jarvis-agent/app/src/main/res/layout/activity_main.xml:6, 24, 52, 126, 160, 448`); Liteshare's 37 hardcoded `Color(0xFF2196F3)` occurrences. Declared-but-unenforced tokens are worse than none, because they create the illusion of a system. Enforce "scheme tokens, not raw colors" with grep, like nexpdf's `docs/UI_ACCEPTANCE_CHECKLIST.md` does.
2. **Empty theme modules and dead duplicate screens.** Liteshare's `lib/src/core/theme/ui_enhancements.dart` is 0 bytes; `features/home/` holds three competing home screens (`home_screen.dart`, `lightshare_home_screen.dart`, `xender_home_screen.dart`) plus `discover_tab.dart` vs `discovery_tab.dart`. Abandoned redesigns left in-tree make the canonical UI unidentifiable. Delete or mark dead.
3. **Dark-only themes with no light counterpart, and hardcoded chrome that breaks the declared theme.** jarvis-agent has no `values-night/`; Liteshare's hardcoded white app bar (`src/widgets/lightshare_app_bar.dart:63`) would silently break its declared `darkTheme`.
4. **Docs claiming tokens that don't exist in code.** linuxify's `docs/UI_REVIEW.md` claims semantic `Spacing` tokens; grep over `app/src/main/java` finds none — components use raw dp (`ui/components/Common.kt` lines 50, 69, 91, 100). Review docs must be verified against source.
5. **God Activities / setState-only state.** jarvis-agent's 722-line `ChatActivity.kt`; Liteshare's `setState` throughout. Upgrade to ViewModel/StateFlow (or equivalent) as screens multiply.
6. **Stock platform icons everywhere.** jarvis-agent's `@android:drawable/ic_menu_*` (`activity_main.xml:31, 78, 221`) kills visual identity even with a good palette; linuxify's and nexpdf's consistent one-family icons are the fix.
7. **Accessibility as an afterthought.** Liteshare: 1 semantics hit across `lib/`; jarvis-agent hardcodes menu strings in layouts while `strings.xml` holds 6 entries. The good counter-examples: contentDescription on every icon (jarvis-agent, linuxify nav), `aria-live`/`aria-hidden` discipline (momotts `index.html:170`).
8. **Repo language ≠ repo content.** momotts is labeled Kotlin and ships only a landing site. Keep source and marketing site in the same repo truthfully separated, and keep claims ("60/120 FPS UI", `features/index.html:170-180`) out of docs until the implementation exists to verify.
9. **Inline hex in components.** ahyeon-s-vision's `Index.tsx:687` (`style={{ color: "#e84040" }}`) — a color that exists nowhere in the token set — is exactly the drift the playbook Law 1 verify grep catches. In an editor with themes, this breaks instantly.
10. **Emoji as UI icons.** ahyeon-s-vision's `pc-icon`, tour flags, and milestone chips violate playbook Law 11; emoji render differently per platform and are unlabelable for screen readers.
11. **Happy-path-only screens.** The playbook's "Every screen is the happy path" critique (PLAYBOOK.md:51). In an editor, the same instinct would leave import failures and render errors unrendered. Every async panel needs loading/empty/error before it counts as done.
12. **Token sets in README prose only.** momostack documents "8pt spacing" and color roles in `README.md`, but nothing enforces them. Tokens need one source file plus lint/grep checks.
13. **Removing focus outlines to make room for a custom cursor.** momostack's `main.css:1289` (`outline: none`) costs keyboard users affordances. Never in an editor.
14. **Dead-end errors.** Playbook rule: "Dead-end errors are bugs" (`AGENTS.md` rule 2). Errors must link to the action that unsticks (retry, re-import, docs).
15. **Fifty unused stock components.** Both Lovable-scaffolded repos ship ~49 shadcn `ui/` components, mostly unused. Keep the component tree to what the product uses.
16. **Content coupled into view files.** ahyeon-s-vision's 1,100-line `Index.tsx` holds all copy and data inline. Keep project data, copy, and view layers separated so the UI can be reasoned about.
17. **Uniform-weight screens.** Playbook Law 9: every card the same elevation, every heading the same size. In a dense editor this is the difference between "where do I look" and a wall of equal cards.
18. **Stale-red-at-top ranking.** Playbook candidate 17: a known, stale, unfixable item in the top slot trains people to skip the top. Rank queues by actionable severity; park known-stale items honestly.
